> **Lens**: A completion script is a second description of a command line, and a second description drifts from the first the moment either changes.
> Generate it from the definitions the parser itself consumes, and where a fact cannot be read from them, gate the restatement with a test that fails when the two disagree.

## Relates to

- Extends [ADR-0013](0013-stdlib-flag-cli.md) (keeps stdlib parsing and hand-rolled dispatch, and makes the hand-rolled table the source completion reads)
- See also [ADR-0024](0024-commands-answer-to-their-initial.md) (the initials completion offers are the table's, so a new command is completable the moment it dispatches)
- See also [ADR-0029](0029-update-owns-the-whole-install.md) (update is what writes the generated scripts to disk)

## Problem

### Symptom

Adding completion to a CLI with no framework meant writing zsh, bash and fish scripts by hand, each restating every command, flag, alias and region word.

### Pain point

Nothing would have failed when they went stale. A renamed flag leaves a script that offers a name the binary rejects, and the user finds out by having the command refuse the completion the shell just gave them.

## Decision

### The lens

- **Given**: there is no CLI framework to generate completion from (ADR-0013), and the flags each command parses are registered in code the parser runs
- **We prefer**: registering every command's flags through a named function that both the parser and the generator call, over hand-written scripts, over adopting a framework for the sake of its completion generator, and over a generator reading a separate flag description
- **Because**: what a shell offers and what the parser accepts then come from one place, and the facts that cannot be read from a FlagSet - one-letter aliases and value candidates - are the only thing a test has to police
- **Unless**: never - a fact that cannot be derived from the registration is declared in the table and gated by the drift test, rather than written into a script

### In practice

- commandTable is the only command set there is - Run dispatches from it, screenz --help renders from it, and all three completion scripts are generated from it.
- Whether a flag takes a value is read from the FlagSet through the same IsBoolFlag interface the parser uses to decide, never restated.
- Each flag's description in the fish script is the usage string the parser was registered with.
- The generator iterates the FlagSet rather than the table, so a flag the parser accepts is offered even before the table catches up.
- TestSpecMatchesTheParser asserts both directions per command; a renamed flag fails the build in the same commit that renames it.
- Value candidates come from the domain - layout.RegionWords, rule.OrderWords, install.Shells - so a new region is completable without touching a shell script.
- Profile names are completed by calling screenz itself and filtering with the embedded jq (ADR-0027), so the script needs no jq on PATH.
- The table is a function, not a package variable, because update reads it back to generate scripts and Go will not initialise a variable that refers to itself.

## Consequences

### Pros

- The three scripts cannot drift from the parser without a test failing, which is the only property that makes shipping completion worth doing.
- A new command or flag is completable in every shell for free, including its one-letter alias and its initial.
- Regenerating is part of an upgrade rather than an errand - screenz update --all rewrites the scripts from the binary that is now installed.

### Cons

- Three shell dialects are rendered by string building in Go, which is harder to read than the scripts it emits and can only be checked by reading the output.
- The fish dialect cannot be syntax-checked without fish installed, so its correctness rests on review and on the shape of the generated output.
- One-letter aliases and value candidates are still declared in the table, not derived; the drift test is what makes that safe rather than the compiler.
